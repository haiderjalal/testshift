# Source-based test generation

This change is local until reviewed, committed and deployed. The production App already monitors CI; source-based generation is a new, disabled-by-default owner-funded pilot. No production migrations, App permission updates, paid model requests or customer PRs were performed while implementing it.

## Customer flow

1. Sign in, install the App on selected repositories, paste a repository URL and approve source analysis plus a test PR. No workflow filename is requested. Existing-workflow monitoring remains available under “Use an existing test workflow instead”.
2. TestShift verifies current user administration and installation access, checks that a repository-scoped write token can be minted, then reserves a generation job. The separate GitHub worker processes it.
3. The worker reads the immutable default-branch commit and source inventory through GitHub. It sends eligible source to Anthropic in one bounded structured-output request. It never clones, installs, imports or runs customer code on Render or Vercel.
4. New Vitest unit/integration tests and Playwright browser tests are validated for allowed paths, basic TypeScript syntax, assertions, category coverage and obvious unsafe content. These checks do not prove semantic correctness or sandbox arbitrary code; the customer must review the PR. Existing application files, package manifests, lockfiles, tests and workflows remain untouched.
5. The App creates one `testshift/tests-JOB_UUID` branch and a PR against the analyzed default branch. The PR includes `.testshift/generated/` and `.github/workflows/testshift-generated.yml`. GitHub Actions executes three independent jobs with an empty disposable PostgreSQL service, no production credentials, read-only checkout and pinned official actions. Existing project scripts can execute during install/dev startup; review them and the proposed tests before using the workflow. Existing workflows may also trigger on the new branch/PR according to their own configuration.
6. Review assertions, coverage gaps, service prerequisites and CI results. Correct failures before merging. Once merged, subsequent pushes and PRs rerun the suite without paying for another AI call. Existing CI remains independent. The signed completion/reporting pipeline publishes verified job and step outcomes; assertion-level coverage remains in the test artifacts, not inferred from a successful job.

## Initial support and limits

- Next.js or Vite at the repository root with a `dev` script, an npm lockfile or a pinned `packageManager: pnpm@X.Y.Z` plus pnpm lockfile. Monorepos, Yarn, non-JavaScript stacks and custom infrastructure require assisted setup. Existing generated suites are detected and not overwritten; automatic incremental regeneration is not implemented.
- Maximum inventory 15,000 entries and GitHub response size 2 MB. Truncated inventories fail explicitly. Read at most 60 eligible files / 140 KB, individual files at most 24 KB. Package manifest first, then existing tests, then other source. The PR lists analysis counts and omissions; this is not whole-codebase coverage for repositories exceeding those bounds.
- Hidden files including `.env` and `.github`, binaries, symlinks, submodules, build/vendor directories, fixtures, secret-named files, lockfile contents and recognizable embedded credentials are excluded. Filtering is best effort, not a guarantee of secret removal. Customers explicitly authorize sharing eligible code with Anthropic. Customer source is never written to the database or logs. Generated code can contain excerpts and is stored privately for recovery for seven days; job metadata lasts 30 days. GitHub keeps PR/code/artifacts under the repository's policy.
- One Sonnet 5.5 request, no automatic SDK retries, input JSON/system/schema bounded to 210 KB, output at most 8,192 tokens. Based on this project's model price table the conservative reservation is under $1/request. Maximum three requests/customer/24h and ten/day globally, reserved transactionally. Uncertain crashed model calls fail rather than spending again. Successful token usage/cost is stored; provider errors or invalid responses may have incurred unrecorded spend, so provider billing remains authoritative.
- Tools use exact Vitest 5.0.3 and Playwright 1.64.0 versions with a checked-in separate toolchain lockfile, installed using `npm ci --ignore-scripts`. Root lockfiles are preserved. Tests may need additional dependencies, login fixtures, database schema/seed or local service setup. Missing prerequisites are gaps/failures, not silently successful coverage.
- Tests use synthetic fixtures and local services. No deployment, production database migration, payment, external account provisioning or destructive production test is generated. Empty PostgreSQL is available but application schema is not automatically applied.
- A successful workflow proves only executed assertions. The agent cannot guarantee exhaustive tests, correct AI-generated assertions or a passing first proposal for every project.

## Owner activation, in order

1. Review this implementation and migration source `supabase/migrations/20261010000000_github_generation.sql`. Back up as appropriate, then use your approved migration process on the same database used by Vercel and Render. It adds three private RLS tables and does not change customer application databases. The migration runner requires explicit owner authorization.
2. In GitHub → Settings → Developer settings → GitHub Apps → **testshiftqa** → Permissions & events, set **Contents: Read and write**, **Pull requests: Read and write**, **Workflows: Read and write**. Retain Actions read, Checks write and Metadata read. Save, then approve the new permissions on each installation. See [GitHub reference creation permissions](https://docs.github.com/en/rest/git/refs#create-a-reference) and [installation token permission scoping](https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app).
3. Deploy the reviewed code to both Vercel and the Render GitHub worker. Keep `GITHUB_GENERATION_ENABLED=0` during the rollout. Render's build still needs `npm ci --include=dev` for tsx and TypeScript; start remains `npm run github:worker`.
4. Add **ANTHROPIC_API_KEY** to Render's GitHub worker secret store. Never put the model key, App key or token encryption key in customer Actions secrets. Existing GitHub/DB variables remain required. The Vercel frontend does not need the model key for this feature.
5. Set **GITHUB_GENERATION_ENABLED=1** on both hosts and redeploy/restart them after the migration and permission update. The UI uses this owner flag; worker execution additionally requires its Anthropic key. Check worker logs and use a disposable Next.js/Vite pilot repository.
6. Connect that pilot using the source-sharing consent. Refresh the repository page, open the generated PR and confirm three actual CI jobs execute. Review the tests before merging; only then offer it to customers. GitHub repository rules, Actions approval settings and organization policy still apply.

## Local validation (2026-10-09)

- Production build, TypeScript, lint, self-check and diff checks passed. Source/generated-client secret scan found no exposure. Production dependency audit and the entire separate generated-tool lockfile audit found zero vulnerabilities.
- Full application/security/database suite: 97 passing tests; action runner: six passing tests. The 11 generation tests were also rerun after validation changes, with the five database/queue tests rerun after adding persistent quota reservations and verifying migration idempotence/RLS. Quotas survive report deletion/disconnect.
- Full browser regression covered 70 desktop/mobile cases: 68 initially passed and two generation-form retry failures revealed an input-reset bug. That bug was fixed; all 18 GitHub browser cases then passed on rerun, including both previously failing cases, consent enforcement, cross-account denial and existing-workflow compatibility.
- `npm run github:validate-generated` executed the exact emitted tools/configuration against a synthetic Vite project: two unit assertions/tests, two integration tests and one Playwright checkout test passed. The AI transport and GitHub publication were mocked in control-plane tests; no paid live model call, real customer code execution or live customer PR was performed.
- An additional audit of the existing development toolchain reported five high-severity advisories through `eslint-config-next → fast-glob → micromatch → braces`. This does not appear in the production dependency or generated-test-tool audits. The suggested forced fix would downgrade Next's ESLint configuration to 14.2.35; it was not applied. Track the upstream patch separately.
- The extra Chromium build downloaded for the synthetic validation and its partial download were removed after testing to restore local disk space. Existing browser installations were preserved.

## Payment

This is an owner-funded generation pilot, not a new checkout. Connecting/generating does not create a paid website-testing order or debit the customer. The owner pays Anthropic usage and the repository owner pays GitHub Actions usage according to their GitHub plan. A paid repository tier needs an agreed price, checkout, payment verification and server-side entitlements before any charging claim is made. The existing Wise website-shift flow remains separate.

## Recovery and revocation

The queue uses exclusive ten-minute leases. Source-fetch failures can retry with a delay. A model call is durably marked before it starts; an uncertain model result is never called again automatically. Saved proposals can retry publication up to five attempts without another AI call. Base trees preserve existing files; branch refs are created once, never force-pushed. Existing branches must match the intended tree and source parent. PR lookup deduplicates successful publication after a lost response, including PRs the customer subsequently closes. A GitHub/DB race can leave a branch/PR after revocation if the API request was already in flight; later work and private data access stop. Disconnect removes generation records through the existing cascade; customer GitHub files and PRs are managed separately.
